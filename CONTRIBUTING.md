## Reporting bugs

Open an issue with enough detail to reproduce it:

- your OS, GPU, and EP
- which example and the steps to trigger it
- what you expected vs. what happened etc

## Changes and features

For small things or bug fixes that you can reproduce just open a pull request. For larger arch changes or features, it helps to open an issue first describing what you're trying to achieve could be really helpful to discuss together :-)

## AI / LLM contribution policy

> This policy is adapted from [GTK's AI contribution policy](https://gitlab.gnome.org/GNOME/gtk/-/blob/main/CONTRIBUTING.md#ai-contribution-policy), with strict guidelines on authenticity, commit hygiene, and code readability.

- **You own it.** If you used an AI tool, you are still 100% responsible for the
  change. "The AI wrote it", "AI suggested it", or "AI verified it" is never an
  explanation, and never an acceptable defense.
- **You must be the Author.** All commits must be authored and committed by **you** 
  (a human). Do not use AI bot accounts, GitHub automated integrations or
  configure your git identity to credit an AI.
  Do not add `Co-authored-by:` or `Assisted-by:` trailers.
- **PR descriptions must reflect your own thoughts (translation is welcome).** 
  Do not paste verbose, synthetic summaries or automated diff recaps 
  generated by an LLM. I/We want a genuine explanation from *you* describing 
  what changed and why. If English is not your first language, using an LLM to 
  translate or polish *your own drafted thoughts* into English is 
  completely fine. The key is that the intent and substance must come from you, 
  and the final text should remain concise and direct.
- **No LLM comment clutter (No over explaining).** LLMs tend to aggressively annotate 
  every single line with obvious explanations. Do not submit code polluted with 
  redundant comments (e.g., `//fast fourier transform -> fn fft(...)` or restating what the code clearly does). 
  Comments must be concise and strictly contextual.
- **Understand and test what you submit.** Build it, run it, and verify it against 
  real test cases. Do not submit code, docs, or tests you cannot explain in detail yourself.
- **Don't fabricate.** No invented benchmarks, fake performance numbers, hallucinated 
  APIs, or synthetic test results.
- **Respect licensing and attribution.** Do not launder proprietary or unvetted code 
  through a model; always credit the foundational work you build on.
- **Disclose usage concisely.** A single sentence in the PR stating what tool was used 
  and how you independently verified the output is enough.

If you can stand behind it and explain it, it's welcome here. That's the whole bar and it's the same bar a human writing every line by hand would meet.
